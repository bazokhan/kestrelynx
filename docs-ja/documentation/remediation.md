# 修正計画と修正PR

!!! warning "実験的な機能"

    修正計画と修正PRは実験的な機能です。設定・通知・PRの形式は今後変わることがあります。

KestreLynxは稼働イメージの所見を基に、イメージや依存パッケージの更新を提案します。
このページでは、修正計画と修正PRの有効化、結果の読み方、配置前に必要な確認を説明します。

候補は変更の提案です。PRの作成やマージだけでは、稼働中のコンテナで脆弱性が解消したことにはなりません。

## 修正計画と修正PRの違い

修正計画と修正PRの有効化設定は別々で、どちらも既定値は`false`です。

| 設定項目 | 行うこと | 行わないこと |
| --- | --- | --- |
| `remediation.enabled` | 候補を選び、対応するイメージの再スキャン結果を比較し、対応付けたソースを読んで計画を通知します。 | GitHubへの書き込み、パッケージマネージャーの実行、作業用コンテナの作成、稼働中のWorkloadの変更は行いません。 |
| `remediation.pull_requests.enabled` | 条件を満たす候補のGitHub PRを作り、言語パッケージの更新を使い捨てのDocker作業用コンテナで実行します。 | PRのマージ、アプリケーションイメージのビルド、変更の配置は行いません。 |

修正計画を無効にしたまま修正PRだけを有効にすると、設定エラーになります。
Kubernetesモードで修正計画を有効にした場合も設定エラーになります。

読み取りだけの修正計画でも、計画と通知の記録はローカルに保存します。
両方の設定が無効の場合、修正計画の処理は行いません。

## 対応範囲と必要なもの

### 対応しているもの

Dockerに対応し、ソースの変更先はComposeのWorkloadに対応付けます。

- 公開の配布イメージ・ベースイメージ
- 公開のnpm・PyPIパッケージ
- Compose・Dockerfile・言語パッケージの変更先となるGitHub上のソース

### 対応していないもの

- Kubernetesモードでの修正計画の有効化（設定エラーになる）
- 非公開のイメージレジストリやパッケージ取得元（GitHub tokenを設定しても対象外）
- GitHub以外のソースの変更先

### 必要なもの

- 実行環境
    - Slackまたは汎用Webhookの通知先を設定した、稼働中のKestreLynx
    - 修正計画とPRの記録を保持する永続ストレージ
    - 言語パッケージのPRを有効にする場合、使い捨ての作業用コンテナを操作できるDocker APIへのアクセス
- ソースの対応付け
    - ComposeのPRを作る場合、編集するファイルとサービスへの対応付け
    - Dockerfileと言語パッケージの場合、計画の作成にも必要なソースの対応付け

配布イメージの比較は、ソースの対応付けがなくても計画に表示できます。

- **GitHubの読み取り**
    - 公開リポジトリはtokenなしで読み取れる
    - 認証が必要な場合は、対応付けたリポジトリだけに限定したfine-grained personal access tokenを使い、計画の読み取りにはContentsのRead権限を付ける
- **PRの作成**
    - 後述する書き込み権限も必要

## 修正計画の有効化手順

### 1. ComposeのWorkloadを確認

対応付けに使うWorkloadキーを確認します。

1. 稼働中のコンテナのラベルからprojectとserviceを取得する
    - project: `com.docker.compose.project`
    - service: `com.docker.compose.service`
2. `compose/<project>/<service>`形式でWorkloadキーを組み立てる

!!! note "Composeプロジェクト名"

    - projectには実際の配置で使っているComposeプロジェクト名を使う
    - Composeプロジェクト名はリポジトリ名やディレクトリ名とは異なることがある

### 2. Workloadとソースを対応付ける

既存の`config.yml`に対応付けを追加します。

- 次のセクションを追加し、例のWorkload、リポジトリ、ブランチ、パスを置き換える
- 対応付けの種類を指定する
    - 各エントリーには`compose`・`dependencies`・`dockerfile`のうち、必ず1種類だけを指定する
    - 同じWorkloadには各種類を1件ずつ設定できるため、複数の種類が必要な場合はエントリーを分ける
- パスとベースブランチを設定する
    - パスはリポジトリのルートからの相対パスにする
    - ルートにある依存ディレクトリは`.`にする
    - それ以外は先頭の`/`、`./`、`..`、バックスラッシュを含まない正規化したパスにする
    - 同じ依存ディレクトリやDockerfileを共有する対応付けでは、ベースブランチを一致させる

```yaml
remediation:
  enabled: true
  pull_requests:
    enabled: false
  storage_dir: /var/lib/kestrelynx/remediation
  mappings:
    - workload: compose/example/web
      repository: example/deployment
      base_branch: main
      compose:
        path: compose.yml
        service: web

    - workload: compose/example/api
      repository: example/application
      base_branch: main
      dependencies:
        directory: .

    - workload: compose/example/app
      repository: example/application
      base_branch: main
      dockerfile:
        path: docker/Dockerfile
        target: runtime
```

!!! note "対応付けとソースの確認"

    - KestreLynxはブランチをコミットに解決してからソースを読む
    - 対応付けは利用者が指定するものであり、パッケージ名と版が一致しても、稼働イメージがそのソースからビルドされたことの証明にはならない

### 3. 記録を永続化

記録の保存先と計画の処理量を設定します。

- `remediation.storage_dir`の保存先を確認する
    - 既定値は`/var/lib/kestrelynx/remediation`で、配布のComposeファイルがマウントする状態データ用ボリュームの中にある
    - 変更する場合は、書き込み可能な永続ストレージ上の絶対パスを指定する
- 計画の処理量は`remediation.limits`で設定する
    - 各項目は次の表を参照し、すべて正の値で指定する

| 設定項目 | 既定値 | 説明 |
| --- | --- | --- |
| `candidate_scans_per_cycle` | `10` | 1サイクルで候補イメージをスキャンする回数の上限です。 |
| `baseline_rescans_per_cycle` | `10` | 1サイクルで比較元イメージを再スキャンする回数の上限です。 |
| `registry_requests_per_cycle` | `200` | 1サイクルのイメージレジストリへの要求数の上限です。 |
| `tag_pages_per_repository` | `20` | イメージリポジトリごとのタグ一覧取得ページ数の上限です。 |
| `cycle_timeout` | `30m` | 計画処理の期限であり、スキャン全体の期限ではありません。 |

!!! note "上限に達した場合"

    - 上限を超える処理は延期として通知する
    - タグ一覧を最後まで取得できなかった場合、その候補を最新パッチとは判断しない

設定の完全な例は
[`config.example.yml`](https://github.com/kitsunetrail/kestrelynx/blob/main/config.example.yml)にあります。

### 4. 設定を読み直してスキャンを確認

設定を読み直し、スキャン結果を確認します。

1. KestreLynxのComposeディレクトリで次のコマンドを実行し、コンテナを作り直してログを表示する

    ```bash
    docker compose up -d --force-recreate kestrelynx
    docker compose logs -f kestrelynx
    ```

2. ログと通知の「修正計画」欄を確認する
    - 既定の`schedule.run_on_start: true`では、起動後にスキャンが始まる
    - 条件を満たす言語パッケージは、最初は依存更新候補として表示される

!!! note "計画で実行する範囲"

    - 計画だけでは更新処理や更新結果の検査は実行しない

## 対象ごとの設定と候補の選び方

### 配布イメージのタグ

`compose`の対応付けで、ソースファイル内の`services.<service>.image`を指定します。

| 稼働中の参照 | 候補の選び方 | 結果 |
| --- | --- | --- |
| `nginx:1.25.3`などの完全な版を指定するタグ | 完全なタグ一覧から、major・minor・接頭辞・接尾辞が同じ最新パッチを選びます。 | 条件を満たす候補は、イメージのタグだけを変えるPRにできます。 |
| `postgres:16`・`1.25`・`latest`などの浮動タグ | 同じタグが現在レジストリで指す内容を候補にします。 | 比較で条件を満たした場合は再取得を案内し、参照が変わらないためPRは作りません。 |
| digestだけ、またはタグとdigestを併記した参照 | 候補を自動では選びません。 | タグ更新の対象外です。 |
| プレリリースや未対応のタグ形式 | 候補を自動では選びません。 | 理由を付けて対象外にします。 |

現在のイメージと候補は、同じスキャナと同じ内容の脆弱性データベースで比較します。

- **候補として提案できる条件**
    - 対象の所見が1件以上なくなる
    - 評価範囲で新しい所見が増えない
    - 必要な解析が完了している
- **一部だけ改善する候補**
    - 提案の対象とし、残る所見は分けて表示する
- **利用者の判断が必要な候補**
    - 所見が増える候補は利用者が判断する
    - 新たにCISA KEV掲載の脆弱性が入る場合も、その旨を通知する

Composeのタグ編集には、次の条件があります。

- **自動編集できる参照**
    - 稼働中のリポジトリとタグに一致する、直接記述されたイメージ参照
- **手動で変更する場合**
    - 変数やdigestを使う参照
    - 編集箇所に未対応のエイリアス、マージキー、`include`、`extends`を使う場合
- **Dockerfileの更新として扱う場合**
    - `build:`を持つサービス

### Dockerfileのベースイメージ

`dockerfile`の対応付けには、ファイルと任意のビルド`target`を指定します。

- **ビルドステージの選択**
    - targetを省略すると最後のステージを使う
    - 選んだステージが前のステージを継承している場合は、外部のベースイメージに到達するまでたどる
- **Composeからの読み取り**
    - Composeの対応付けがあり、`build:`がリポジトリ内の静的なcontextと任意の`dockerfile`・`target`を指定している場合は、そこから読み取れる
    - この場合、Dockerfileの対応付けを別に追加する必要はない
    - 両方を設定した場合は、内容を一致させる必要がある

| ベースの参照・入力 | 候補の選び方と扱い |
| --- | --- |
| `python:3.12.3-slim`などの完全な版を指定するタグ | 現在のベースと、major・minor・接頭辞・接尾辞が同じ最新パッチを比較し、該当する`FROM`のタグだけを変える候補を作ります。 |
| `python:3.12-slim`などの浮動タグ | ベースのレイヤーを確認しますが、タグ更新PRや更新前後の脆弱性件数の比較は行いません。 |
| ベースのレイヤーが稼働イメージの先頭のレイヤーと一致しない場合 | その比較が稼働イメージのベースを表すとは判断しません。 |
| `FROM`の変数、digest参照、`scratch`、未対応のビルド命令 | 手動での対応が必要です。 |
| Composeのリモートbuild context、`dockerfile_inline`、`additional_contexts` | そのbuild設定からDockerfileの自動編集先を決めません。 |

- **浮動タグのベースを確認できない場合**
    - 通知では`docker compose build --pull`で現在のベースを取得して再ビルドする手順を案内する
    - この案内は再ビルドの手順であり、改善を確認した結果ではない
- **ベースイメージの比較対象**
    - Trivyが一致するベースのレイヤーに属すると報告した所見だけを対象にする
    - 後のレイヤーにある所見や、利用できるレイヤー情報のない所見は、ベース由来の対象として扱わない

### 言語パッケージ

`dependencies`の対応付けには、依存ファイルがあるディレクトリを指定します。

| マネージャー | 対応するファイルと形式 | 更新の扱い |
| --- | --- | --- |
| npm | 単一プロジェクトの`package.json`と、`lockfileVersion`が2または3の`package-lock.json`です。 | lockfileを更新し、必要な場合は対応する直接依存の版指定も変更します。 |
| pnpm | `package.json`と、`lockfileVersion: '9.0'`でimporterが`.`だけの`pnpm-lock.yaml`です。 | lockfileと対応する直接依存の版指定を更新し、選ばれた版を検査します。 |
| pip | 対応する公開PyPIの依存指定を記述した`requirements.txt`です。 | 厳密な`==`固定と、記載されている場合はハッシュを更新し、範囲指定が修正版を許す場合はPRではなく再ビルドの見込みを通知します。 |
| uv | 単一プロジェクトの静的な`pyproject.toml`と、`version = 1`・`revision = 5`の`uv.lock`です。 | lockfileと対応する直接依存の版指定を更新します。 |

稼働イメージの所見から、パッケージごとに更新目標の下限を選びます。

- **選定対象**
    - スキャンの状態が`fixed`で修正版情報がある所見
    - 修正版情報のない所見は対象外
- **下限の決め方**
    1. 対象の各所見について、稼働版より新しい最小の報告修正版を求める
    2. その最大値をパッケージの更新目標の下限にする
- **選定後の検査**
    - 下限の選定だけでは、対象の脆弱性がすべて解消することを確認したことにはならない
    - PR有効時に更新後の依存ファイルを別途検査し、更新前後のスキャンを比較して、対象の脆弱性が検出されなくなったことを確かめる
    - パッケージマネージャーが実際に選んだ版を検査して通知するため、下限と採用された版が異なることがある

直接依存の範囲が修正版を許さない場合は、演算子を保ち、版の部分だけを書き換えられます。

| マネージャー | 書き換えに対応する版指定 |
| --- | --- |
| npm・pnpm | `1.2.3`・`=1.2.3`・`^1.2.3`・`~1.2.3` |
| uv | `==`・`~=` |

推移的依存の更新は、宣言された依存の範囲内に限ります。
修正版を入れるために親パッケージを更新したり、overridesを追加したりはしません。

次の入力や更新結果は、主に手動での対応が必要になります。

- 未対応のソース構成
    - workspaceや、依存ファイルを一意に決められない構成
    - Git・URL・ローカル・未対応のレジストリを取得元とする依存
    - 動的なプロジェクトメタデータや、ソースのビルドが必要な依存
- 依存の制約とインストール時の動作
    - 書き換えが必要で、対応する形式に含まれない版指定
    - 依存を同梱するパッケージや独自のshrinkwrapを持つパッケージ、およびその配下の依存
    - 未対応のオプション、別ファイルの読み込み、評価できない環境マーカーを使うpipの依存指定
- パッケージマネージャーの制限
    - `requires-python`が作業用イメージのPython 3.13を許さない、または評価できないuvプロジェクト
    - revision 5以外の`uv.lock`
    - pnpmで公開から24時間以内の版を扱い、公開後の経過時間の検査で拒否されたり、未許可の設定ファイルが作られたりする更新
    - lockfileの形式を書き換えたり、説明できない変更を加えたりする更新

## 修正PRの有効化手順

### 1. GitHub tokenとリポジトリのCIを準備

PRの作成に必要なtokenとリポジトリの設定を準備します。

- 対応付けたリポジトリだけに限定したfine-grained personal access tokenを作り、次のリポジトリ権限を付ける

| 権限 | アクセス |
| --- | --- |
| Contents | Read and write |
| Pull requests | Read and write |

- PRを有効にする前に、ワークフローとリポジトリの規則を確認する
    - PRを作ると、`pull_request`を契機とするワークフローなど、リポジトリのCIが起動することがある
- tokenを`remediation.github.token`に設定する
    - `config.yml`は所有者だけが読めるようにする
    - `config.yml`はコミットしない

### 2. Dockerへのアクセスと作業用イメージを確認

言語パッケージの更新に使う作業用イメージとDockerへのアクセスを確認します。

- 作業用イメージの参照を設定する
    - 本体に組み込まれた参照を使う場合は、`remediation.worker.image`を省略する
    - ミラーや検証用イメージに置き換える場合は、`repository@sha256:<小文字の16進数64桁>`の形式で指定する
    - 作業用イメージの参照を含まないビルドでは、明示的に指定する
- Docker APIのプロキシを経由する場合は、作業用コンテナの操作を許可する設定にする

!!! note "作業用イメージの取得と制約"

    - 言語パッケージの更新には、本体のリリースごとにdigestで固定した`ghcr.io/kitsunetrail/kestrelynx-worker`を使う
        - KestreLynxは更新で初めて必要になったときに取得する
        - タグだけの指定は受け付けない
    - 作業用イメージを取得できない場合、言語パッケージの更新は延期する
        - 代わりに本体コンテナ内でパッケージマネージャーを実行することはない

!!! warning "Docker APIへのアクセス"

    - 修正PRを有効にすると、言語パッケージの更新のためにDocker APIで作業用コンテナを作成・起動・削除する
    - Docker socketを`:ro`でマウントしても、API操作は制限されない
    - 配布のsocketマウントは`:ro`のまま利用でき、`:rw`へ変更する必要はない

### 3. PRの作成を有効化

既存の対応付けを残し、remediationセクションを更新します。

1. 次の設定でPRの作成を有効にする

    ```yaml
    remediation:
      enabled: true
      pull_requests:
        enabled: true
      github:
        token: "REPLACE_WITH_YOUR_GITHUB_TOKEN"
    ```

2. KestreLynxを起動する前に、プレースホルダーを準備したtokenに置き換える
3. PRと依存更新の処理量を`remediation.limits`の次の項目で設定する
    - 件数は正の値で指定する
    - `job_timeout`は`1m`から`60m30s`までの値で指定する

| 設定項目 | 既定値 | 説明 |
| --- | --- | --- |
| `new_prs_per_cycle` | `3` | 1サイクルで新しく作るPR数の上限です。 |
| `open_prs` | `10` | 設定したリポジトリ全体で開いておけるKestreLynxのPR数の上限です。 |
| `dependency_jobs_per_cycle` | `3` | 1サイクルで試みる依存更新の単位数の上限です（パッケージ数やコンテナ数ではありません）。pipの単位やmanifestを編集する単位など、1つの単位で複数のコンテナを使うことがあります。 |
| `job_timeout` | `6m` | 各作業用コンテナの作成・実行・結果回収の期限です。後片付けには別途30秒の期限を使います。 |

!!! note "期限と上限の扱い"

    - コンテナ内の処理には、`job_timeout`より30秒短い期限を渡す
    - 上限に達した処理は延期する
        - 開いているPR数の枠を空けるために、古いPRを閉じることはない

### 4. 最初の結果を確認

KestreLynxを作り直し、最初の結果を確認します。

1. 修正計画の導入時と同じ手順でKestreLynxを作り直す
2. 通知、ログ、GitHub上のPRを確認する
3. 検証結果を読む前に、次の項目が意図したものかを確認する
    - リポジトリ
    - ベースブランチ
    - ファイル
    - 提案された版

## 通知の読み方

Slackでは`Fix plan`、`notify.language: ja`では「修正計画」の欄に表示します。

| Slackの区分 | 意味 | 次に行うこと |
| --- | --- | --- |
| `re-pull` / `再pull` | 同じイメージタグの新しい内容を取得することを、比較結果が支持しています。 | イメージを再取得してサービスを作り直し、稼働イメージのスキャンを確認します。 |
| `update candidate(s)` / `更新候補` | イメージの比較、または検査済みの依存更新に基づく候補です。 | 候補やリンク先のPRを確認します。 |
| `dependency update candidate(s)` / `依存更新候補` | ソースに対象の依存が見つかり、目標の版を選んだ状態です。 | 提案された版を確認し、更新処理はまだ実行されていないことに注意します。 |
| `rebuild expected` / `再ビルドで解消見込み` | pipの範囲指定が修正版を許しています。 | 再ビルドし、実際に入った版と配置結果を確認します。 |
| `manual` / `要判断` | ソース、更新処理、比較結果に利用者の判断が必要です。 | 理由を読み、手動で変更を準備または評価します。 |
| `not comparable` / `比較不能` | 比較に必要な証拠が足りないか、条件が一致していません。 | スキャンした実体、解析範囲、表示された理由を確認します。 |
| `deferred` / `延期` | 上限、期限、レート制限、作業用イメージの取得不可などで処理できませんでした。 | 理由を確認し、原因への対応後または次のサイクルで再試行します。 |
| `no candidate` / `候補なし` | 新しい内容がないか、候補で対象の所見が解消しませんでした。 | 利用できる版と残る所見を確認します。 |
| `excluded` / `対象外` | 自動で候補を探す対象に含まれない参照です。 | 参照を確認し、必要な場合は手動で更新します。 |
| `failed` / `失敗` | 処理に失敗しました。 | 理由とログを確認します。 |

- **PRの集計**
    - 計画とは別に、作成、オープン、マージ済み、未マージでクローズ、要判断、延期、停止・失敗に分けて表示する
    - マージ済みは、配置を確認した状態ではない
- **検査範囲と注意の表示**
    - Dockerfileの結果には、ベースイメージだけの比較であることを付記する
    - 言語パッケージのPRには、依存ファイルを検査した結果であり、再ビルドしたイメージは未確認であることを付記する
    - majorが変わる場合は、追加の注意を表示する
- **結果を確認する場所**
    - Slackは件数を集計し、名前を出す結果を数件に絞る
    - 汎用Webhookの`remediation`オブジェクトでは、PR処理を含む個別の結果と理由を確認できる
    - 保存された計画には、PR処理前の計画と依存更新の結果が含まれる

Webhookの送信とペイロードについては、
[KestreLynxの仕組み — 汎用Webhook](how-it-works.md#7-webhook)を参照してください。

## PRの読み方と確かめている範囲

PR本文は次の構成です。

| 節 | 内容 |
| --- | --- |
| `What` | リポジトリ、ベースブランチとコミット、ソースファイル、対象のWorkloadです。 |
| `Change` | 変更前後のイメージタグやパッケージの版です。 |
| `Why this candidate` / `Why these versions` | 候補を選んだ規則です。 |
| `Verification` | 比較結果、スキャン条件、実行した検査です。 |
| `Not verified` | 利用者に残る確認と配置作業です。 |

- **PR本文の補足**
    - 言語パッケージのPRには、対象の脆弱性、manifestの編集、実行した操作、lockfileで追加・変更・削除された項目も記載する
    - PR本文は英語

| 対象 | KestreLynxが確かめていること | 確かめていないこと |
| --- | --- | --- |
| 配布イメージ | 現在と候補のイメージの実体、比較できるスキャン条件、なくなる・残る・増える所見です。 | アプリケーションの互換性、CIの成功、マージ後の配置です。 |
| Dockerfileのベースイメージ | ベースのレイヤーの一致と、対象の所見についての現在と候補のベースイメージの比較です。 | ビルドの来歴や、変更後のDockerfileから再ビルドしたイメージの所見です。 |
| 言語パッケージ | 更新結果、公開レジストリと照合した変更後の配布物の参照と整合性情報、修正版の条件、許可されたファイル変更、依存ファイルの更新前後のTrivy filesystemスキャンです。 | 再ビルドしたイメージでの解消、アプリケーションの互換性、テストの成功です。 |

検査範囲には、次の制約があります。

- **言語パッケージのfilesystem比較**
    - 更新対象以外のパッケージも含めた依存ファイルを比較する
    - 前後で同じ内容のデータベース、深刻度の範囲、スキャン設定を使う
    - リポジトリ独自のTrivy設定、ignoreファイル、VEX文書は読まない
- **Trivyのレイヤー情報**
    - イメージの作られ方を証明するものではない
    - 後のDockerfile命令で同じパッケージの同じ版を入れ直しても、ベースのレイヤーに属すると報告されることがある
    - 後のビルド命令で最終イメージの所見が変わることもある
- **依存ファイルの検査**
    - 依存の組み合わせがレジストリの宣言と完全に一致することと、出力の形式をインストーラが受け付けることは、可能な範囲でしか確認しない

マージ前に、提案された依存ファイルからインストールするCIを実行してください。

| マネージャー | CIでのインストール確認例 |
| --- | --- |
| npm | `npm ci` |
| pnpm | `pnpm install --frozen-lockfile` |
| pip | `pip install -r requirements.txt` |
| uv | `uv sync --locked` |

比較はすべて、設定した深刻度の範囲に限ります。
PRの`Resolved`はその比較結果を表し、稼働中のコンテナの現在の状態を表すものではありません。

!!! warning "majorの変更"

    - **変更が必要になる場合**
        - 対象の脆弱性をすべて直すために、別のmajorへの更新が必要になることがある
        - 0.xのパッケージではminorの変更を同じように扱う
    - **マージ前の確認**
        - manifestの編集も含めてPRと通知の注意を確認する
        - 互換性のテストを実行する

## PRの管理と利用者の作業

KestreLynxは更新を記録し、GitHub上の状態と照合します。

- 既存の更新
    - すでにPRがある更新は重複して作らない
    - 未マージで閉じた更新は、ブランチを削除した後も作り直さない
    - 言語パッケージの更新入力が同じ場合、依存更新ジョブを再実行せず、開いているPRに対応付けられる
- ブランチと置き換え
    - 既存のブランチを上書きしたりforce更新したりしない
    - 利用者が変更したと判定したPRは自動置き換えの対象にしない
    - 新しい候補は既存PRのブランチを書き換えず、新しいPRにする

古いPRを閉じるには、置き換えの条件を満たす必要があります。

- **置き換えの条件**
    - 新しいPRを作成し、同じ編集箇所で古いPRの修正対象をすべて引き継ぐと確認できる
    - イメージの置き換えでは、同じ系列のより新しいパッチであることも必要
    - 言語パッケージでは、別のパッケージだけの更新や、古い対象の一部しか含まない更新では置き換えない
- **置き換え時の処理**
    - 置き換え前に両方のPRを確認し、古いPRに置き換え先のリンクをコメントしてから閉じる
    - 新しいPRの作成、確認、置き換えコメントに失敗した場合、古いPRは開いたまま残す

レビューしてマージした後も、配置は利用者が行います。

1. マージされたソースの変更を再取得する
2. 更新された配布イメージを取得するか、変更後のDockerfileと依存ファイルからアプリケーションイメージを再ビルドする
3. 必要に応じて再ビルドしたイメージを公開し、対象のサービスを再作成・再配置する
4. その後のKestreLynxによる稼働イメージのスキャンで、対象の所見を確認する

- **稼働中のコンテナへの反映**
    - 浮動タグではソースが変わらなくても、再取得または再ビルドとコンテナの再作成が必要
    - ソースの変更をマージしただけでは、古いコンテナが動き続ける

## 権限・通信・セキュリティ

### GitHub token

- **権限と用途**
    - tokenは指定したリポジトリへのアクセスに使う
    - PRの作成を有効にした場合は、ソースとPRへの書き込みにも使う
    - KestreLynxはGitHub APIでコミット、ブランチ、PR、置き換えコメントを作り、置き換えられたPRを閉じる
- **送信先と保護**
    - tokenの送信先は`api.github.com`
    - 作業用コンテナにはtokenを渡さない
    - 設定ファイルを保護し、必要なリポジトリだけに権限を限定する

### Docker socketと作業用コンテナ

- **本体のDocker socket**
    - `:ro`でマウントしていても、Docker APIの操作を許可する
- **作業用コンテナへの入力**
    - 処理に必要な依存ファイルを渡す
    - GitHub token、本体の設定、Docker socketは渡さない
- **実行時の制限**
    - 非rootで動き、Linux capabilitiesをすべて削除し、no-new-privilegesを設定する
    - メモリ、CPU、プロセス数、出力量、時間を制限する
    - パッケージのスクリプトとソースのビルドは無効にする
- **書き込み先とファイル権限**
    - 配布作業用イメージでは、非rootのジョブが書き込めるのは容量を制限したtmpfsだけ
    - Dockerのroot filesystem設定自体は読み取り専用ではなく、所有者とファイルの権限でイメージの書き込みレイヤーと入力ディレクトリをジョブから保護する
    - `remediation.worker.image`で上書きするイメージにも、同じ所有者・権限の制約が必要
    - 参照形式やdigestの検証では、イメージ内の全ファイルの権限を実行時に検査しない
- **結果の回収と後片付け**
    - 終了後に標準出力から結果を回収してコンテナの削除を試み、その後に回収した結果を本体が信頼しない入力として検査する
    - 結果を回収できていれば、削除に失敗しても検査を続ける場合がある
    - 削除失敗は記録し、後続の後片付けで再試行する

### 外向きの通信と通知される情報

| 通信先 | 用途と情報 |
| --- | --- |
| GitHub API | 対応付けたリポジトリとファイルの読み取り、PR状態の照合、有効時の変更とPR本文の書き込みに使います。 |
| 公開イメージレジストリと、その認証・ダウンロード先 | タグの一覧取得、イメージの実体の解決、比較用イメージの取得に使います。 |
| Trivyのデータベース用レジストリ | 比較に使う脆弱性データベースの取得に使います。 |
| `ghcr.io`、または設定した作業用イメージのミラー | Dockerによる作業用イメージの取得に使います。 |
| `registry.npmjs.org` | 公開npmパッケージのメタデータと配布物の取得に使います。 |
| `pypi.org`・`files.pythonhosted.org` | 公開PyPIパッケージのメタデータと配布物の取得に使います。 |
| 設定したSlack・Webhookの通知先 | 所見、計画の結果、ソースの場所、版の変更、理由、PRのリンクや操作結果を送ります。 |

- **作業用コンテナの通信**
    - Dockerのbridgeネットワークを使う
    - 通信先を許可リストで制限する構成ではない
- **共有される情報**
    - 計画やPRには、イメージ参照とdigest、Workload名、リポジトリ名、ファイルパス、パッケージの版、脆弱性IDが含まれることがある
    - これらを共有できる通知先とリポジトリの公開範囲を選ぶ
- **その他の通信**
    - 通常のスキャンや任意の脅威情報フィードの通信も引き続き行う

### 保存される記録

- 通常のスキャン通知の状態とは別に、`remediation.storage_dir`の下へ記録を保存する

| ファイル | 内容 |
| --- | --- |
| `plan.json` | PR処理前に保存した最新の計画、ソースの場所、スキャンの証拠、更新の検査です。 |
| `delivered.json` | 最後に通知した計画の識別用ハッシュです。 |
| `prs.json` | PRの識別情報、更新と試行の記録、再作成を抑止する情報、GitHub操作の記録です。 |

- **PR処理後の結果**
    - PR処理の結果・操作イベント・問題は、`plan.json`の保存後に通知用の計画へ追加する
    - これらを含めて`plan.json`を再保存することはない
    - PR処理の結果はWebhook・Slackで、PRと操作の保存記録は`prs.json`で確認する
- **保存期間と上限**
    - PRと再作成抑止の記録には有効期限を設けない
    - 操作履歴は1,000件を上限とし、未通知の操作や結果が確定していない操作は削除から保護する
    - 安全に空きを作れない場合は書き込みを止める
- **記録の復旧と保護**
    - 破損した計画・PRの記録や未対応の形式を、空の記録に置き換えて処理を続けることはない
    - PRの記録がない場合は、書き込みの前に`kestrelynx/`ブランチの開いているPRと閉じたPRを調べ、本文の識別マーカーから復旧を試みる
    - 照合できない記録がある場合は書き込みを止める
    - 記録を永続化し、PRの識別マーカーを残す

## 候補やPRが出ない場合

まず、保存された計画や汎用Webhookの`category`・`reason`・`detail`を読み、
KestreLynxのログを確認します。

| 状況・代表的な理由 | 確認する場所 |
| --- | --- |
| 計画に項目がない | 稼働イメージのスキャン結果、対象の深刻度、修正版が報告されている所見を確認します。 |
| `no_newer_tag`・`same_content`・`candidate_does_not_resolve_targets` | 利用できるタグ、現在の内容、候補で対象の所見が変わるかを確認します。 |
| ソースがない、`not_found_in_source`、依存ファイルが曖昧 | Composeのproject・serviceラベル、対応付けのパス、ベースブランチ、GitHubへのアクセス、ソース内のパッケージの版を確認します。 |
| `base_layers_mismatch`・`floating_base_unconfirmed` | Dockerfileのtarget、稼働イメージで使われたベース、表示された再ビルドの案内を確認します。 |
| `introduced_findings`・`introduced_kev` | 手動更新を判断する前に、候補の比較で増えた所見を確認します。 |
| `analysis_incomplete`・`entity_unverified`・データベースの準備失敗 | スキャンの失敗、イメージの実体、platform、解析範囲、データベース取得のログを確認します。 |
| 未対応のlockfile・取得元・制約・Python環境 | 前述の対応形式と、手動になる条件を確認します。 |
| `unexpected_files`・`release_age_violation`・更新結果の検査失敗 | 更新の詳細、パッケージマネージャーの動作、依存ファイルを確認します。 |
| `work_image_not_configured`・`work_image_unavailable` | 組み込まれた、または上書きしたdigest付き参照、イメージへのアクセス、Docker APIの権限を確認します。 |
| スキャン・レジストリ・ジョブ・PRの上限 | `remediation.limits`、レート制限の応答、次の実行予定を確認します。 |
| 候補はあるがPRがない | PRの有効化、tokenの権限、ソースを編集できる条件、閉じた更新の再作成抑止、PRの状態と理由を確認します。 |
| GitHubへの書き込み失敗・結果不明 | リポジトリの規則、tokenのアクセス、操作記録を確認し、結果不明の書き込みは再試行前にKestreLynxが照合します。 |
| 保存失敗・記録の照合不能 | 永続ボリュームへのアクセス、空き容量、ログ、既存PRのマーカーを確認します。 |

再試行を強制するためにPRの記録を削除しないでください。
閉じた更新の再作成を抑止し、過去の操作を照合するために必要な記録です。
