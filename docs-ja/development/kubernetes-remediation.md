# Kubernetes での修正 PR の開発

- **状態:** 実装済み(検証用のホストで PR の作成から GitOps による反映まで確認)
- **開始日:** 2026年10月20日
- **最終更新:** 2026年10月23日

## 目的

[修正計画と修正 PR](remediation-pull-requests.md)を Kubernetes でも使えるようにする。
直す場所は利用者に明示してもらい、言語パッケージの更新はクラスタの中の使い捨ての Pod で安全に動かす設計にする。

## 修正の対象と流れ

Git で管理するマニフェストに `image: nginx:1.27.2` と書かれた Deployment が動いているとする。
修正版が 1.27.3 なら、そのタグを書き換える PR を作る。

変更前のマニフェストの抜粋:

```yaml
containers:
  - name: web
    image: nginx:1.27.2
```

PR で提案する変更後の抜粋:

```yaml
containers:
  - name: web
    image: nginx:1.27.3
```

```text
稼働中のイメージ → 修正候補の比較 → Git のファイルを変更する PR
                                              ↓ 利用者がマージ
                                  利用者の GitOps・CI → クラスタへ反映
```

通常のマニフェストに加え、Kustomize の `images` と Helm の `values` に書かれたイメージの指定も対象にする。

KestreLynx は修正をクラスタへ適用しない。
マージ後の反映は利用者の GitOps・CI が行い、自動同期が有効ならマージがそのまま反映になる。

## 方針

- **直す場所は利用者が対応付けで明示し、Argo CD や Flux の情報から推測しない**
    - 管理元の情報だけでは、変更すべきリポジトリやファイルを特定できないため
- **Pod に書かれている版・動いている版・リポジトリのファイルの版の3つが一致したときだけ PR にする**
    - 稼働中の対象とは異なる版をもとに変更を作らないため
- **Compose と同じく、digest で固定した参照は手動での対応にする**
    - タグの更新とは別の変更規則が必要になるため

## 決定事項

### 作用範囲の明示(`affects`)

Helm の1つのキーや Kustomize の1つの指定が、複数のワークロードに効くことがある。
KestreLynx は Helm や Kustomize を展開しないので、効く範囲を推測せず、設定に書いてもらう。

次は、Helm の `image` キーが、対応付けた `web` の `app` に加えて `worker` の `app` にも効く場合の設定例である。
`affects` には、対応付けたコンテナ以外の作用先を、種類・namespace・名前・コンテナ名で列挙する。

```yaml
remediation:
  mappings:
    - workload: deployment/shop/web/app
      repository: example/deployment
      base_branch: main
      helm_values:
        path: releases/shop/values.yaml
        key: image
        affects:
          - deployment/shop/worker/app
```

`affects` がなければ、利用者が「対応付けたコンテナだけに効く」と確認したものとして扱う。
念のため、同じ namespace などで同じ値を使う未記載のワークロードを見つけたら PR の作成を止めるが、記載漏れをすべて見つけられるわけではない。

### 言語パッケージの更新の実行方式

Docker ではパッケージマネージャーを作業用コンテナで動かしているが、対象のクラスタ内には Docker がない。
外部の Docker ホストを使う案は利用者の準備の負担が大きいため採らず、作業専用の namespace に使い捨ての Pod を作る方式にした。

Pod を作る権限は、利用者が言語パッケージの更新を有効にしたときだけ、その作業用 namespace に限って付ける。

### 作業用 Pod の安全策

言語パッケージの更新は Kubernetes 1.30 以降を対応対象とし、次の安全策を設ける。

- クラスタの標準機能である ValidatingAdmissionPolicy で作れる Pod の形を固定し、KestreLynx は作業前に違反する Pod の試し作成が拒否されることを確かめる
- 作った Pod の実際の中身が許可した形と一致することを確かめてから、更新元のファイルを渡す
- 結果は作業ごとの鍵で暗号化し、結果の本文は暗号文だけをログに残す
- GitHub のトークンや KestreLynx の設定は作業用 Pod に入れない

## 検証結果

確認した範囲では、修正 PR の作成、既存の PR との対応付け、GitOps による反映、条件が整わない場合の停止は想定どおりに動いた。
検証で見つかった2点とその対応は、末尾の「検証で見つかった点」にまとめた。

### 修正 PR

言語パッケージの更新と依存元からの再解決は、作業用 Pod で実行した。

| 形式 | 変更内容 |
| --- | --- |
| マニフェスト | 通常のコンテナ・ネイティブサイドカー・CronJob のイメージ行を1つの PR で更新し、コメントと引用符を保った |
| Dockerfile | `FROM` のベースイメージを更新した |
| Kustomize | `newTag` だけを変更した |
| Helm values | タグの値だけを変更した |
| npm・pnpm | lockfile だけを変更し、minimist を 1.2.5 から 1.2.8 に更新した |
| pip | ハッシュ値を含む `requirements.txt` を変更し、urllib3 を 1.26.4 から 2.8.0 に更新した |
| uv | `pyproject.toml` と `uv.lock` を変更し、urllib3 を 1.26.4 から 2.8.0 に更新した |
| npm・pnpm の依存元からの再解決 | lockfile で依存元の mkdirp を 0.5.1 から 0.5.6 に上げ、minimist を 0.0.8 から 1.2.8 に更新した |

uv の依存元からの再解決は、候補に含まれる certifi の公開から72時間が経過していないため待機となり、検証中には PR を作成しなかった。

### 繰り返し実行と記録の復元

| 状況 | 結果 |
| --- | --- |
| 同じ更新を繰り返し実行 | PR は重複せず、既存の PR に対応付けられた |
| Dockerfile と pip の PR を閉じて再起動 | 同じ更新の PR は作り直されなかった |
| インスタンスの識別情報を残してローカルの記録を削除 | PR 本文の印から既存の PR と閉じた PR の状態を復元できた |

### GitOps による反映

| 状況 | 結果 |
| --- | --- |
| GitOps 管理下のアプリの PR を作成 | PR 本文に Flux の Kustomization または Argo CD の Application を管理元として表示した |
| マージ後に Flux と Argo CD の変更の取得を促す | マージから約2分で Deployment と CronJob に更新が反映された |
| CronJob の更新が反映 | 新しく始まる Job は新しい版で動き、稼働中の Job は古い版のまま終了まで動いた |
| ロールアウト中や古い Job の稼働中に、新旧の版の混在やファイルとの不一致を検出 | 手動での対応となり、修正 PR の作成・更新を止めた |
| ロールアウトが完了 | 同じ更新を再び提案しなかった |

### 手動での対応になる場合

| 状況 | 結果 |
| --- | --- |
| digest で固定したイメージ参照 | 手動での対応となり、同じファイルの更新を止めた |
| `$imagepolicy` の目印がある行 | 別のツールがタグを管理しているため、手動での対応となった |
| Kustomize の作用範囲に記載漏れがある | 同じ namespace で同じイメージを使うワークロードが `affects` にないため、更新を止めた |
| Helm の `affects` に稼働していないワークロードがある | 稼働中の対象を確認できないため、更新を止めた |

### 作業用 Pod の安全策

| 状況 | 結果 |
| --- | --- |
| KestreLynx の権限を確認 | Pod の作成は作業用 namespace に限定され、対象への書き込みや Secret・ConfigMap の読み取りは拒否された |
| 規則違反の Pod の作成と、作成規則の適用が外れた状態を確認 | 検証した規則違反の Pod はすべて拒否され、規則の適用を確認できない場合も作業用 Pod を作らなかった |
| 管理者が実行中の作業用 Pod を変更 | ラベル・注釈・イメージ・既存の toleration の変更と、一時コンテナの追加は拒否された |
| 作業用 namespace の Pod 数の割り当てを使い切る | 作業用 Pod を作らず待機した |
| 作業中に KestreLynx が再起動 | 残った作業用 Pod を起動時に削除した |
| 言語パッケージ更新時のログ・終了メッセージ・Pod の情報・Event を確認 | 収集した情報に、入力や結果の平文は見つからなかった |
| 同じ NetworkPolicy を適用した検証用 Pod で、制限が効いた後に通信を確認 | 確認した接続先では、CoreDNS への DNS と外部の TCP 443 番だけに届いた |

通信制限の適用までに数秒かかった点は、次の「検証で見つかった点」に記載した。

### 検証で見つかった点

#### 削除中の作業用 Pod による待機

| 項目 | 内容 |
| --- | --- |
| 起きたこと | 削除中の作業用 Pod を同時実行数の上限に数え、次の作業が待たされていた |
| 対応 | 削除中の Pod を数えないように修正した |
| 確認結果 | [`max_concurrent_pods`](../documentation/configuration.md#remediation-worker-kubernetes) が1でも、削除中の Pod による言語パッケージの項目の待機は起きなかった |

#### 新しい Pod への通信制限の適用時間

| 項目 | 内容 |
| --- | --- |
| 起きたこと | 検証した K3s の既定の CNI では、新しい Pod に NetworkPolicy が効くまでの数秒間、送信が制限されなかった |
| 対応 | KestreLynx からは制御できない制限として、[外向きの通信](../documentation/outbound-communication.md#worker-network)に記載した |

## 未検証・次の作業

- **実際の GitHub での PR の置き換え**
    - 同じ系列に新しいパッチ版がなかったため、古い PR を新しい PR に置き換える動作は実環境では確かめられず、単体テストでのみ確認した
- **結果の大きさと実行環境**
    - ノードのログの上限を超える大きな結果の扱いは、実環境での確認が残る
    - 新しい版の K3s や、他の Kubernetes ディストリビューションでの動作は未検証
- **手動での対応になる指定の追加確認**
    - `${VAR}` を含む参照、`newTag` のない Kustomize の項目、空の Helm のタグは、単体テストでのみ確認した
